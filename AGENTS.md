# Lab-FON — Development Instructions

## 1. Project

Lab-FON is an academic, non-profit institutional website for the Laboratório de Fonética da UFRJ.

The project must prioritize:

- simplicity;
- maintainability;
- accessibility;
- portability;
- low operating cost;
- technological independence;
- long-term institutional continuity.

The project is intended to be maintained by developers other than its original author and must not depend on the continuous availability of any particular developer, AI agent, SaaS provider, or hosting platform.

---

## 2. Production environment

The production site is hosted on shared hosting provided by the PPGLEV.

Production access is limited to FTP.

The production environment must be assumed to have:

- no root access;
- no Node.js runtime;
- no persistent application server;
- no database server;
- no backend application;
- no requirement for SSH;
- no server-side build process.

Therefore:

> **The production site must remain a static website.**

Do not introduce a backend, database, server-side application, or other runtime service unless this constraint is explicitly changed by the project maintainer.

The production server should be treated as a destination for the files generated by the project, not as part of the application's runtime architecture.

---

## 3. Core architecture

The project follows a static-first architecture:

```text
Structured Content
       ↓
   DataAdapter
       ↓
   Renderers
       ↓
      Vite
       ↓
 Static Build
       ↓
      FTP
       ↓
 PPGLEV Hosting
```

Preserve this architectural separation.

The application code is responsible for presentation and behavior.

Structured data is responsible for content.

The build process produces the files deployed to production.

---

## 4. Content and presentation

Content must remain separated from presentation.

Do not hard-code institutional content into rendering components when that content belongs in the project's data model.

Do not make rendering components directly dependent on a specific data-storage format.

The existing `DataAdapter` abstraction should be preserved.

The `JSONAdapter` is the current local/static data implementation.

If a new data source is introduced, prefer implementing the appropriate adapter rather than bypassing the abstraction.

Components and renderers must not directly manipulate the underlying data source.

---

## 5. JSON

JSON is a data format, not the intended user interface for content editing.

The current JSON-based architecture should be preserved where appropriate, but future development should allow non-technical users to edit content through a graphical interface rather than manually editing JSON.

Do not replace JSON merely because a newer format or technology exists.

Change the data model only when there is a concrete requirement.

When the data model is expanded, preserve:

- clear semantics;
- consistent naming;
- explicit required and optional fields;
- referential integrity;
- backward compatibility where practical.

Use schema validation when it provides a meaningful improvement in data integrity.

---

## 6. Page structure

The long-term editorial model may allow non-technical users to modify the composition of pages.

This should be implemented through predefined components or blocks rather than unrestricted HTML/CSS/JavaScript editing.

The distinction is:

```text
User controls:
    content
    ordering of supported sections
    composition of supported page blocks

Developer controls:
    HTML
    CSS
    JavaScript
    component behavior
    design system
    accessibility implementation
```

Do not turn the project into an unrestricted visual page builder unless this requirement is explicitly introduced.

The visual/editorial system should preserve the site's design consistency and accessibility.

---

## 7. Future desktop editor

A future Windows desktop editor is an intended direction of the project.

Its conceptual workflow is:

```text
Open local project
       ↓
Edit content and page structure
       ↓
Validate
       ↓
Preview locally
       ↓
Build
       ↓
Publish through FTP
```

The editor should hide technical operations such as JSON manipulation, Vite execution, build management, and FTP deployment from non-technical users.

However:

> **Do not implement the desktop editor unless the current task explicitly concerns it.**

Do not introduce Electron, Tauri, FTP libraries, desktop packaging, or other editor-specific dependencies merely because they are mentioned in this document.

---

## 8. Dependencies

Prefer existing project capabilities over new dependencies.

Before adding a dependency:

1. verify whether the required functionality already exists;
2. consider whether a native web/API solution is sufficient;
3. evaluate maintenance status and maturity;
4. evaluate bundle/build impact;
5. evaluate licensing;
6. consider long-term institutional maintainability.

Do not add dependencies solely because they are fashionable or technologically newer.

Do not replace an existing dependency without a concrete technical benefit.

For this project, simplicity and longevity are more important than adopting the newest technology.

---

## 9. Accessibility

Accessibility is a core project requirement.

Maintain the project's commitment to WCAG 2.1 AA.

New or modified functionality should preserve, as applicable:

- semantic HTML;
- keyboard navigation;
- visible focus;
- adequate color contrast;
- meaningful alternative text;
- accessible form controls;
- correct heading hierarchy;
- appropriate ARIA usage;
- understandable error messages;
- compatibility with assistive technologies.

Do not treat accessibility as a later optimization.

---

## 10. Security

The public site is static and should remain so unless explicitly authorized otherwise.

Never commit:

- FTP passwords;
- API keys;
- access tokens;
- private credentials;
- secrets;
- personal information that is not intended for publication.

Do not introduce authentication or server-side mechanisms unless they are explicitly required.

Deployment credentials must remain outside the source repository.

---

## 11. Testing and validation

Before considering a significant change complete:

1. run the relevant tests;
2. run the production build;
3. verify that the build succeeds;
4. check for regressions;
5. check accessibility when the interface is affected;
6. verify that generated assets and paths are correct.

Tests should verify behavior and contracts rather than implementation details.

Every new feature or component containing meaningful logic should have appropriate tests.

Do not remove or weaken tests merely to make an implementation pass.

---

## 12. Git and source control

GitHub is the source of truth for the project's source code.

Keep commits focused and meaningful.

Do not mix unrelated changes in the same commit.

Before modifying the repository:

- inspect the current state;
- identify relevant existing implementations;
- preserve uncommitted user changes;
- avoid destructive Git operations.

Never reset, revert, delete, or overwrite user work without explicit authorization.

---

## 13. Working with AI agents

The AI agent is an implementation assistant, not the project's autonomous architect.

For non-trivial tasks, follow this sequence:

```text
Understand
    ↓
Inspect relevant code
    ↓
Plan
    ↓
Implement
    ↓
Test
    ↓
Review
```

Before making substantial changes:

- inspect the relevant files;
- identify existing abstractions;
- determine whether the requested behavior already has an appropriate extension point;
- avoid unnecessary architectural changes.

For significant architectural decisions, explain the proposed approach before implementing it.

Do not rewrite large portions of the project when a localized change is sufficient.

Do not introduce functionality that was not requested merely because it appears useful.

---

## 14. Preserve existing architecture

The project already contains deliberate abstractions, including the adapter and renderer patterns.

Prefer extending existing abstractions over creating parallel mechanisms.

In particular:

- do not bypass `DataAdapter` without justification;
- do not introduce direct data access into renderers;
- do not duplicate existing rendering logic;
- do not create competing abstractions for the same responsibility.

Before introducing a new abstraction, determine whether an existing one can reasonably be extended.

---

## 15. Change discipline

Favor small, incremental, reversible changes.

For each task:

- modify only what is necessary;
- preserve existing behavior unless the task requires changing it;
- avoid unrelated refactoring;
- avoid speculative features;
- avoid premature optimization.

If a requested change exposes a genuine architectural problem, identify it explicitly rather than silently redesigning the system.

---

## 16. Decision principle

When multiple technically valid solutions are available, prefer the solution that:

1. requires less infrastructure;
2. introduces fewer dependencies;
3. is easier to understand;
4. is easier to test;
5. is easier to maintain;
6. is easier to replace;
7. remains compatible with static hosting;
8. minimizes long-term operational cost.

The project should not pursue technological sophistication for its own sake.

> **The goal is not to build the most sophisticated website possible.**
>
> **The goal is to build a sustainable academic website that can be maintained and used by the community for many years.**
